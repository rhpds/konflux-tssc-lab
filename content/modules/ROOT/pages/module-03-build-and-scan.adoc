= Build and Scan
:navtitle: Build and Scan

Estimated time: *20 minutes*

With your application onboarded and the first pipeline run complete from Module 2, you are ready to see the full build cycle in action.
In this module, you push a small code change to your GitLab repository, watch Konflux respond automatically with a new pipeline run, and then examine the artifacts it produces: a container image, an SPDX Software Bill of Materials (SBOM), and a SLSA provenance attestation.
By the end, you will know what the pipeline produces, where those artifacts land, and how to inspect them.

== Learning Objectives

By the end of this module, you will be able to:

* Build a container image by pushing a source change to GitLab and observing the resulting Konflux PipelineRun.
* Analyze the automatically generated SPDX SBOM to identify its packages, licenses, and vulnerability data.
* Observe how the pipeline scan tasks report findings and how results surface in the Konflux UI.
* Verify that the built image and its associated SBOM and attestation artifacts are present in the Quay registry after the pipeline completes.

== 1. Trigger a Build with a Code Change

Pipelines-as-Code watches your GitLab repository.
Any push to the default branch starts a new PipelineRun automatically.
You will make a minimal change using the GitLab web editor — no local tooling required.

. Open link:{gitlab_url}/{gitlab_username}/sample-component-golang[your GitLab sample repository,window=_blank].

. In the file list, click `README.md`.
On the file view page, click the *Edit* dropdown button and select *Edit single file*.
+
.GitLab Edit dropdown showing the Edit single file option
image::module-03-readme-edit.png[GitLab README.md file view showing the Edit dropdown button expanded with Open in web IDE and Edit single file options,800]

. Scroll to the bottom of the file.
Add a new line:
+
----
# Lab update - module 03
----

. In the *Commit message* field, enter:
+
----
chore: trigger module-03 build
----

. Leave *Commit directly to the `main` branch* selected and click *Commit changes*.

. Confirm the new commit appears at the top of the repository's *Commits* list.
+
.GitLab commit history showing the new commit
image::module-03-commit-history.png[GitLab Commits page showing the new chore: trigger module-03 build commit at the top of the list,800]

. Switch to the link:https://konflux-ui-konflux-ui.{openshift_apps_domain}[Konflux UI,window=_blank].
Navigate to *Applications → my-sample-app → Activity*.

. Within 30–60 seconds, a new PipelineRun entry appears in the Activity feed, linked to the commit you just pushed.
+
.Konflux Activity tab showing the new PipelineRun triggered by the push
image::module-03-activity-new-run.png[Konflux Activity tab listing a new PipelineRun entry triggered by the chore: trigger module-03 build commit,800]

=== Verify

[%interactive]
* [ ] The commit `chore: trigger module-03 build` appears in the GitLab commit history.
* [ ] A new PipelineRun entry appears in the Konflux Activity tab within 60 seconds of the push.

== 2. Trace the Pipeline Stages

The Konflux UI shows the full task graph for each PipelineRun.
You will walk through the stages of the `docker-build-oci-ta-min` pipeline to understand what each task does and where the image digest comes from.

. In the Konflux Activity tab, click the commit entry for `chore: trigger module-03 build` to open its detail view.

. Click the *Pipeline runs* tab to see the pipeline runs linked to this commit.
You will see two runs: a *Build* run (`sample-component-golang-...`) and a *Test* run (`my-sample-app-enterprise-contract-...`).
+
.Konflux commit detail — Pipeline runs tab showing the build and enterprise contract runs
image::module-03-pipeline-runs-tab.png[Konflux commit detail view with the Pipeline runs tab selected showing a Build pipeline run and an enterprise contract Test pipeline run,800]

. Click the *Build* PipelineRun name (the one ending in `-on-push-...`) to open the full task graph.
Do not click the enterprise contract Test run — that is covered in a later module.
+
.Konflux PipelineRun detail showing the task graph
image::module-03-pipelinerun-detail.png[Konflux PipelineRun detail page showing the task graph with each stage displayed as a connected node,800]

. Review the task stages.
The build pipeline runs the following tasks:
+
[cols="1,3",options="header"]
|===
|Task |What it does
|`init`
|Sets up the pipeline workspace and resolves build credentials.
|`clone-repository`
|Clones the exact source commit from GitLab into the pipeline workspace.
|`prefetch-dependencies`
|Pre-fetches Go module dependencies into the trusted artifact store so the build has no outbound network access.
|`build-container`
|Builds the container image using Buildah and pushes it to Quay.
|`build-image-index`
|Creates a multi-architecture image index pointing to the built image manifest.
|`deprecated-base-image-check`
|Flags any base images that have been marked deprecated in the Red Hat container catalog.
|`clamav-scan`
|Scans the image filesystem for known malware signatures using ClamAV.
|`sast-shell-check`
|Runs ShellCheck static analysis on any shell scripts found in the image layers.
|`sast-unicode-check`
|Detects bidirectional Unicode control characters that could hide malicious code.
|`rpms-signature-scan`
|Verifies that all RPM packages in the image are signed with a trusted Red Hat GPG key.
|`tpa-scan`
|Submits the image to Trusted Profile Analyzer for supply chain analysis.
|===

. Click the `build-container` task node.
A side panel opens on the right with two tabs: *Details* and *Logs*.
+
On the *Details* tab, look for the *Results* section.
It lists `IMAGE_DIGEST`, `IMAGE_REF`, `IMAGE_URL`, and `SBOM_BLOB_URL` directly — no log-scrolling needed.
Copy the `IMAGE_DIGEST` value (it looks like `sha256:03359...`).
+
TIP: Click the *Logs* tab if you want to see what Buildah actually did — it shows each layer being pushed and is useful for troubleshooting slow or failed builds.
+
IMPORTANT: Save the digest in a text editor now — you will need it in the next section and again in Module 4.
If you lose it, click back into this task node's *Details* tab to retrieve it.

. Wait for the PipelineRun to reach *Succeeded*.
This typically takes 3–6 minutes.

. In the terminal, confirm the run status:
+
[source,bash,role="execute",subs="attributes+"]
----
oc get pipelineruns -n {openshift_username}-tenant
----
+
Expected output: the most recent PipelineRun shows `SUCCEEDED` in the `REASON` column.

=== Verify

[%interactive]
* [ ] All task nodes in the Konflux PipelineRun detail show a green tick.
* [ ] You have copied the image digest (`sha256:...`) from the `build-container` task logs.
* [ ] `oc get pipelineruns -n {openshift_username}-tenant` shows the run status as `SUCCEEDED`.

== 3. Inspect the SBOM

Every successful `docker-build-oci-ta-min` pipeline run pushes an SPDX SBOM alongside the container image.
The SBOM is stored in Quay as an OCI artifact attached to the image via cosign.
You will download and examine it using the `cosign` CLI in the terminal.

. Set up registry credentials for cosign.
Konflux creates an image-pull secret in your tenant namespace when your component is registered.
Extract it to the standard Docker credential store so cosign can authenticate automatically:
+
[source,bash,role="execute",subs="attributes+"]
----
COMPONENT=$(oc get component -n {openshift_username}-tenant -o jsonpath='{.items[0].metadata.name}')
mkdir -p ~/.docker
oc get secret ${COMPONENT}-image-pull -n {openshift_username}-tenant \
  -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d > ~/.docker/config.json
echo "Credentials configured for: ${COMPONENT}"
----
+
Expected output: `Credentials configured for: sample-component-golang-...`

. Retrieve the base image path that Konflux assigned to your component:
+
[source,bash,role="execute",subs="attributes+"]
----
export IMAGE_BASE=$(oc get component -n {openshift_username}-tenant \
  -o jsonpath='{.items[0].spec.containerImage}' | cut -d: -f1)
echo "Base image path: ${IMAGE_BASE}"
----

. Set the digest you copied from the `build-container` task logs.
Replace `sha256:PASTE_YOUR_DIGEST_HERE` with your actual digest value:
+
[source,bash,subs="attributes+"]
----
export IMAGE_DIGEST=sha256:PASTE_YOUR_DIGEST_HERE
----

. Construct the full image reference:
+
[source,bash,role="execute",subs="attributes+"]
----
export IMAGE_REF="${IMAGE_BASE}@${IMAGE_DIGEST}"
echo "Full image ref: ${IMAGE_REF}"
----

. Set the cosign environment variable needed for this lab's self-signed TLS certificate:
+
[source,bash,role="execute"]
----
export COSIGN_INSECURE_SKIP_TLS_VERIFY=true
----
+
NOTE: Skip TLS verification is required here because the lab Quay instance uses a self-signed certificate.
Do not use this setting in production environments.

. Download and pretty-print the SBOM:
+
[source,bash,role="execute",subs="attributes+"]
----
cosign download sbom "${IMAGE_REF}" | jq .
----
+
The output is an SPDX 2.3 JSON document generated by syft.
The top-level `packages` array lists every package found in the image layers.
+
NOTE: You will see two warnings. The first says SBOM attachments are deprecated — this is expected; the `cosign download sbom` mechanism is being phased out in favour of attestations, which you will use in Module 4. The second warns that this download does not ensure authenticity — also expected, and also addressed in Module 4 when you use `cosign download attestation` to retrieve a cryptographically signed version.
For now, the goal is simply to inspect what the SBOM contains.
+
.cosign SBOM output in the terminal
image::module-03-sbom-output.png[Terminal window showing the SPDX JSON output from cosign download sbom with the packages array expanded,800]

. Count the total number of packages in the SBOM:
+
[source,bash,role="execute",subs="attributes+"]
----
cosign download sbom "${IMAGE_REF}" | jq '.packages | length'
----
+
For this minimal Go sample application you will see a small number of packages — typically under ten.
The exact count can vary as the base image or application dependencies are updated, so do not be concerned if your number differs slightly.
This list is the complete dependency inventory that downstream policy engines and security teams use to evaluate the image.

. Inspect a single package entry to see the fields tracked for each dependency:
+
[source,bash,role="execute",subs="attributes+"]
----
cosign download sbom "${IMAGE_REF}" | jq '.packages[1] | {name, versionInfo, licenseDeclared}'
----
+
Each package entry includes at minimum: `name`, `versionInfo`, and `licenseDeclared`.
Most entries also include an `externalRefs` array containing a `purl` (Package URL), which uniquely identifies the package across ecosystems and is the format used by vulnerability scanners such as Grype and Trivy.
+
NOTE: Some entries show `UNKNOWN` or `NOASSERTION` for version or license — this is normal for internal build artifacts. Try incrementing the index (`packages[2]`, `packages[3]`, etc.) to find entries with richer metadata such as a real version string and a declared license like `BSD-3-Clause`.

=== Verify

[%interactive]
* [ ] `cosign download sbom` returns a JSON document with a populated `packages` array.
* [ ] At least one package shows `name`, `versionInfo`, and `licenseDeclared` fields.
* [ ] `jq '.packages | length'` returns a number greater than zero.

== 4. Review Artifacts in Quay

Konflux pushes the container image and its provenance artifacts to Quay for every successful build.
You will confirm the image is present, verify the digest, and review the source provenance labels embedded in the image before moving to Module 4.

. Open the *Quay* tab.
Log in with `{quay_user}` / `{quay_password}` if prompted.

. Navigate to the repository for your component.
The path follows this pattern:
+
[source,subs="attributes+"]
----
{quay_url}/tsf/{openshift_username}-tenant/<your-component-name>
----
+
TIP: Print the base image path from your terminal to get the exact URL: `echo "${IMAGE_BASE}"`.

. In the *Tags* view, locate the tag that matches the pattern `<component>-on-push-<hash>-build-container`.
This is the container image your pipeline just built.
Click that tag to open the image detail page.
+
.Quay image repository showing the pipeline build tag and the associated attestation artifact
image::module-03-quay-tags.png[Quay image repository tags view showing the container image tag with its digest and a separate dot-git attestation artifact tag,800]

. On the image detail page, confirm the following:
+
[cols="1,3",options="header"]
|===
|Field |What to check
|*Digest*
|Matches the `sha256:...` value you copied from the `build-container` task results — the same bytes the pipeline signed and attested.
|*Vulnerabilities*
|Shows *None Detected* — the ClamAV and RPM signature scan tasks found no issues.
|*Labels*
|Expand the *Labels* section and look for `org.opencontainers.image.source` (the GitLab repository URL) and `vcs-ref` (the exact commit SHA that triggered the build).
These OCI standard labels make the image's origin verifiable without reading pipeline logs.
|===

. Return to the repository's tag list.
Alongside the image tag, you will see an artifact tag ending in `.git` (for example, `0e5bb074...c27.git`).
This is the SLSA provenance attestation stored as an OCI artifact — an in-toto statement that records which source commit, which pipeline, and which cluster produced this image.
You will retrieve and verify it in Module 4.

=== Verify

[%interactive]
* [ ] The Quay repository for your component shows the `<component>-on-push-...-build-container` image tag.
* [ ] The image digest shown in Quay matches the digest you copied from the pipeline logs.
* [ ] The image labels include `org.opencontainers.image.source` and `vcs-ref` confirming the source commit.
* [ ] A `<commit-sha>.git` artifact tag is listed alongside the container image tag.

== Learning Outcomes Checkpoint

Before moving on, check that you can answer the following:

*What artifacts does Konflux push to Quay for every successful build, and why are they kept separate?*

The pipeline produces multiple artifacts stored in Quay.
The container image is what runs in production.
The SLSA provenance attestation — visible in Quay as a `<commit-sha>.git` OCI artifact — is a cryptographically verifiable record of which source commit, which pipeline, and which cluster produced the image.
The SPDX SBOM is stored as an OCI artifact and retrieved via `cosign download sbom` rather than appearing as a named tag in the Quay UI.
Keeping them separate means each artifact can be verified, stored, and consumed independently by different tools and teams.

*What provenance information is embedded directly in the image labels, and why does that matter?*

Every image Konflux builds carries OCI standard labels baked into the image manifest: `org.opencontainers.image.source` links back to the exact GitLab repository URL, and `vcs-ref` records the exact commit SHA that triggered the build.
These labels are visible directly in Quay without retrieving any attestation — anyone can verify at a glance which source produced the image, independent of the build system.
In Module 4 you will see how the SLSA attestation provides a cryptographically signed version of this same claim.

*What makes the image digest important for later modules?*

The image digest (`sha256:...`) is an immutable, content-addressed identifier.
It uniquely identifies the specific byte sequence of the image — changing even one byte produces a different digest.
Signing (Module 4) and policy checks (Module 5) operate on this digest, not on a mutable tag.
That means you can prove that the artifact you sign, test, and release is the exact same artifact the build pipeline produced — nothing more, nothing less.

*What format is the SBOM in, and why does that matter for downstream tooling?*

The pipeline generates SPDX 2.3-format SBOMs using syft.
SPDX is an ISO-standardised open standard (ISO/IEC 5962:2021) supported by the majority of vulnerability scanners, software composition analysis platforms, and regulatory frameworks.
Using a standard format means the SBOM you downloaded today is directly consumable by tools such as Grype, Trivy, or Red Hat Advanced Cluster Security without any conversion step.

== Key Takeaways

* The Konflux build pipeline runs entirely in-cluster on OpenShift Pipelines (Tekton) — no external CI system is required.
* Every successful build produces multiple artifacts in Quay: the container image, an SPDX SBOM (accessible via cosign), and a SLSA provenance attestation stored as a `<commit-sha>.git` OCI artifact.
* OCI image labels (`org.opencontainers.image.source`, `vcs-ref`) embed source provenance directly in the image manifest — verifiable in Quay without reading any attestation.
* SPDX SBOMs enumerate all packages in the image, giving security teams a complete dependency inventory without re-scanning the running container.
* The image digest is immutable and content-addressed — it is the stable reference used for signing and policy gating in later modules.
* Pipelines-as-Code makes build triggers automatic and auditable: every build traces back to the exact source commit that started it.
