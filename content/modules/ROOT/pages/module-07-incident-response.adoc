= Real-World Incident Response
:navtitle: Real-World Incident Response

Estimated time: *15 minutes*

You have a complete supply chain running.
This module shows what it is actually protecting against — not just from the CLI, but inside Konflux itself, from the moment a bad image enters the pipeline to the point where a release attempt is blocked.

You will simulate a real incident, watch Konflux catch it at the Integration stage, and trace the evidence trail that explains exactly what went wrong.

== The Scenario

A developer is under pressure to ship a critical fix immediately.
They build an image locally and push it straight to the Quay registry — skipping Konflux entirely.
No pipeline ran, so no signing step ran, no SBOM was generated, and no SLSA provenance was recorded.
The lab provides a pre-built image that represents exactly this artifact.

The developer then submits a Snapshot pointing to that image and requests a release.

You will play the on-call engineer who discovers the blocked release and traces it back to the root cause.

== 1. Set the Unsigned Image Reference

The lab provides a pre-built unsigned image that simulates the developer's out-of-band push.
Set it in your terminal:

[source,bash,role="execute",subs="attributes+"]
----
export HOTFIX_IMAGE="{quay_hostname}/tsf/unsigned-image:latest"
echo "Hotfix image: ${HOTFIX_IMAGE}"
----

=== Verify

[%interactive]
* [ ] `$HOTFIX_IMAGE` is set in your terminal.

== 2. Create a Snapshot and Watch the Integration Pipeline Fail

In a real incident, a developer might create a Snapshot manually to test whether a hotfix image can be released — bypassing the normal build pipeline.
Conflict creates a Snapshot manually with `oc apply`.
When the Snapshot is created, Konflux automatically triggers the Integration pipeline against it.

. Create the Snapshot:
+
[source,bash,role="execute",subs="attributes+"]
----
cat <<EOF | oc apply -f -
apiVersion: appstudio.redhat.com/v1alpha1
kind: Snapshot
metadata:
  name: hotfix-snapshot
  namespace: {openshift_username}-tenant
spec:
  application: my-sample-app
  components:
  - name: sample-component-golang
    containerImage: ${HOTFIX_IMAGE}
EOF
----

. Switch to the Konflux UI.
Navigate to your `my-sample-app` Application and click the *Snapshots* tab.
+
You will see `hotfix-snapshot` appear in the list within a few seconds.
Notice it has no *Commit message* or *Reference* — distinguishing it from pipeline-built Snapshots, which carry a Git commit reference.
+
.Konflux Snapshots tab showing hotfix-snapshot in the list
image::module-07-snapshot-list.png[Konflux Snapshots tab showing hotfix-snapshot with a dash in the Commit message and Reference columns,800]

. Click *hotfix-snapshot* to open its detail view, then click the *Pipeline runs* tab.
+
Wait 2–3 minutes if the run is still in progress.
When complete, you will see the enterprise contract pipeline run listed with *Status: Failed* and *Type: Test*.
+
.hotfix-snapshot Pipeline runs tab showing the enterprise-contract run as Failed
image::module-07-snapshot-failed.png[Konflux Snapshot detail Pipeline runs tab showing the enterprise-contract pipeline run with Failed status and Test type,800]

. In the terminal, check the Snapshot conditions to confirm the failure state:
+
[source,bash,role="execute",subs="attributes+"]
----
oc get snapshot hotfix-snapshot -n {openshift_username}-tenant \
  -o jsonpath='{.status.conditions}' | jq .
----
+
Expected output — two conditions are key:
+
----
[
  {
    "lastTransitionTime": "2026-11-12T20:27:35Z",
    "message": "Snapshot integration status condition is finished since all testing pipelines completed",
    "reason": "Finished",
    "status": "True",
    "type": "AppStudioIntegrationStatus"
  },
  {
    "lastTransitionTime": "2026-11-12T20:27:35Z",
    "message": "Some Integration pipeline tests failed",
    "reason": "Failed",
    "status": "False",
    "type": "AppStudioTestSucceeded"
  }
]
----
+
`AppStudioIntegrationStatus: True / Finished` means the Integration pipeline *completed* — it ran to the end.
`AppStudioTestSucceeded: False / Failed` means the tests *failed* — the Conforma check found violations.

== 3. Attempt a Release and Observe the Block

The developer, unaware of the failure, submits a release request pointing at the failed Snapshot.

. Create the Release:
+
[source,bash,role="execute",subs="attributes+"]
----
cat <<EOF | oc apply -f -
apiVersion: appstudio.redhat.com/v1alpha1
kind: Release
metadata:
  name: hotfix-release-attempt
  namespace: {openshift_username}-tenant
spec:
  snapshot: hotfix-snapshot
  releasePlan: production-release
EOF
----

. Check the Release conditions.
If you run this immediately after creating the Release, you will see `Released: False / Progressing` and `TenantPipelineProcessed: False / Progressing` — the release pipeline is still running.
Wait approximately one minute, then run:
+
[source,bash,role="execute",subs="attributes+"]

oc get release hotfix-release-attempt -n {openshift_username}-tenant \

The key signal is `ManagedPipelineProcessed: False / Failed`.
The release is not blocked at creation time — the Release Service accepts the request and starts the pipeline.
The managed pipeline runs, executes `ec validate image` against the hotfix image, finds no signature and no SLSA provenance, and fails.
`Released: False / Failed` is the result.
+
NOTE: `Validated: True / Succeeded` and `TenantPipelineProcessed: True / Succeeded` both passing is expected — the Release reference is structurally valid and the tenant-side steps succeed.
The block is in the managed namespace pipeline, where Conforma policy is enforced at release time.

== 4. Investigate the Root Cause

The Release is blocked and the Snapshot failed — now trace back to the specific violation.
The Integration pipeline ran `ec validate image` as a task.
You can read the same violation detail directly.

. Run `ec validate image` against the hotfix image to read the same violations the Integration pipeline saw.
This uses the same policy reference as Module 5:
+
[source,bash,role="execute",subs="attributes+"]
----
ec validate image \
  --image "${HOTFIX_IMAGE}" \
  --policy enterprise-contract-service/lab-policy \
  --certificate-identity-regexp 'https://kubernetes.io/namespaces/.*/serviceaccounts/build-pipeline-.*' \
  --certificate-oidc-issuer {tas_oidc_issuer} \
  --rekor-url https://rekor-server-tsf-tas.{openshift_apps_domain} \
  --output json | jq '[.components[].violations[] | {rule: .metadata.code, msg: .msg}]'
----
+
Expected output:
+
[source,json]
----
[
  {
    "rule": "builtin.attestation.signature_check",
    "msg": "Image signature verification failed: no signatures found"
  },
  {
    "rule": "builtin.provenance.slsa_provenance_available",
    "msg": "No SLSA provenance attestation found from a trusted builder"
  }
]
----
+
These are the exact violations the Integration pipeline recorded.
The root cause is unambiguous: the image was never processed by a Konflux build pipeline, so no signature and no SLSA provenance exist.

. Confirm there are no attestations attached to this digest:
+
[source,bash,role="execute"]
----
cosign download attestation "${HOTFIX_IMAGE}" | jq -s 'length'
----
+
Expected output: `0`
+
Zero attestations means no SBOM and no SLSA provenance.
Conforma cannot determine the build origin, the pipeline that produced it, or whether the source commit is known.

=== Why the Block Is Permanent

The signing certificate is issued to the Tekton Chains service account identity — an identity that only exists inside a running Konflux pipeline.
There is no approved path for an out-of-band image to acquire a valid Konflux signature or SLSA attestation after the fact.

A developer who tries `cosign sign` manually produces a signature tied to their personal OIDC identity — not the Tekton Chains service account — and `cosign verify --certificate-identity-regexp 'https://kubernetes.io/namespaces/.*/serviceaccounts/build-pipeline-.*'` will still fail.
The correct remediation is to open a merge request to the source repository and let Konflux run the build.

[%interactive]

* [ ] `cosign download attestation` returns `0` attestations.

== 5. Clean Up

Remove the failed Snapshot and Release before moving on.

[source,bash,role="execute",subs="attributes+"]
----
oc delete release hotfix-release-attempt -n {openshift_username}-tenant
oc delete snapshot hotfix-snapshot -n {openshift_username}-tenant
----

Expected output: `release.appstudio.redhat.com "hotfix-release-attempt" deleted` and `snapshot.appstudio.redhat.com "hotfix-snapshot" deleted`.

== Key Takeaways

* Konflux evaluates every Snapshot through the Integration pipeline automatically.
  A manually created Snapshot from an unsigned image triggers the same policy check as a pipeline-built Snapshot — and fails for the same reason.

* The release pipeline re-evaluates Conforma policy in the managed namespace at release time.
  The managed pipeline runs `ec validate image` against the image and fails if the evidence is missing — the same violations that blocked the Integration test.
  A human reviewer is never required; the block is automatic and consistent.

* The violation evidence is readable.
  `ec validate image` produces the same violation detail the Integration pipeline logged, so an on-call engineer can confirm the root cause without digging through pipeline task logs.

* Signatures are issued to pipeline identities.
  A personal `cosign sign` does not substitute for a Tekton Chains signature — the certificate identity check will fail regardless of whether the image bytes match.
