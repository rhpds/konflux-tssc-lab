= Release to Production
:navtitle: Release to Production

Estimated time: *15 minutes*

This module closes the end-to-end supply chain.
You release the policy-verified, signed artifact from your tenant namespace to a production Quay registry through Konflux's controlled release pipeline.
You inspect the ReleasePlan and ReleasePlanAdmission that govern the release, trigger a release from the Konflux UI, watch the pipeline re-evaluate Conforma policy at release time, and then verify that the signed image and its attestations are present in production.
The module ends by walking the full chain — from source commit to signed, provenance-attested, policy-gated production artifact — to confirm every link is in place.

== Learning Objectives

By the end of this module, you will be able to:

* Configure and trigger a Konflux ReleasePlan to initiate the controlled release pipeline for a policy-passing Snapshot.
* Verify that the release pipeline re-evaluates Conforma policy before promoting the artifact with the production tag.
* Verify the signed image and its attestations are present in Quay with the production tag after a successful release.
* Trace the artifact from the source commit through signing, policy validation, and production release to demonstrate end-to-end supply chain integrity.

== 1. Create the ReleasePlanAdmission and ReleasePlan

A Konflux release requires two objects: a *ReleasePlanAdmission* in the managed namespace (platform team controls this) and a *ReleasePlan* in your tenant namespace (you create this).
Neither side can push an image to production without the other.
This separation prevents any single team from unilaterally bypassing release policy.

[IMPORTANT]
====
**Lab vs Production:**

In a production environment, the *ReleasePlanAdmission* is pre-created by platform administrators in the managed namespace.
Application developers do NOT have permissions to create or modify it — they can only reference it from their tenant-side ReleasePlan.

For this lab, you will create the ReleasePlanAdmission yourself to understand:

* What controls the managed release pipeline
* How the platform team gates production access
* What policies and validations are enforced

In real deployments, you would only create the ReleasePlan (tenant side) and reference a pre-existing ReleasePlanAdmission that the platform team set up.

**How the matching works:**

When you trigger a release:

1. The Release Service reads your ReleasePlan's `application` field (my-sample-app) and `target` field ({openshift_username}-managed)
2. It looks in the target namespace for a ReleasePlanAdmission that has `my-sample-app` in its `applications` list
3. It verifies the ReleasePlanAdmission's `origin` field matches your tenant namespace

The **application name** is the key link between the two resources.

This creates bidirectional authorization:

* ReleasePlan says: "I want to release **my-sample-app** to **{openshift_username}-managed**"
* ReleasePlanAdmission says: "I accept releases of **my-sample-app** from **{openshift_username}-tenant**"

Both must match for the release to proceed.
====

You will create the ReleasePlanAdmission first (platform side), then create the ReleasePlan through the Konflux UI (tenant side).

. Create the ReleasePlanAdmission in the managed namespace:
+
[source,bash,role="execute",subs="attributes+"]
----
cat <<EOF | oc apply -f -
apiVersion: appstudio.redhat.com/v1alpha1
kind: ReleasePlanAdmission
metadata:
  name: production-release
  namespace: {openshift_username}-managed
spec:
  applications:
  - my-sample-app
  origin: {openshift_username}-tenant
  policy: release-policy
  pipeline:
    pipelineRef:
      resolver: git
      params:
      - name: url
        value: https://github.com/rhpds/konflux-tssc-lab.git
      - name: revision
        value: main
      - name: pathInRepo
        value: tekton/pipelines/managed-release.yaml
EOF
----
+
Expected output: `releaseplanadmission.appstudio.redhat.com/production-release created`
+
This object runs the `managed-release.yaml` pipeline in the managed namespace — it validates the release with Enterprise Contract and pushes the image to production.

. Now create the ReleasePlan through the Konflux UI.
Switch to the *Konflux* tab.

. Verify you are in your tenant namespace `{openshift_username}-tenant` (check the namespace selector at the top of the page).

. Navigate to *Applications → my-sample-app*.

. Click the *Release plans* tab in the left navigation.

. Click *Create release plan*.

. Fill in the form:
+
* *Name*: `production-release`
* *Application*: `my-sample-app` (should be pre-selected)
* *Target*: `{openshift_username}-managed`
+
NOTE: The *Application* and *Target* fields are how the ReleasePlan connects to the ReleasePlanAdmission. Konflux looks in the `{openshift_username}-managed` namespace for a ReleasePlanAdmission that has `my-sample-app` in its `applications` list and `{openshift_username}-tenant` in its `origin` field. The matching is based on the **application name**, not the resource names.
+
* Expand *Git options for the release pipeline* section:
** *Git URL for the release pipeline*: `https://github.com/rhpds/konflux-tssc-lab.git`
** *Revision*: `main`
** *Path in repository*: `tekton/pipelines/tenant-release.yaml`
* *Auto release*: Off (leave toggled off for manual releases)
* *Standing attribution*: Off (leave toggled off)
* Click *Create*

. Verify both resources were created.
In your terminal:
+
[source,bash,role="execute",subs="attributes+"]
----
oc get releaseplan -n {openshift_username}-tenant
oc get releaseplanadmission -n {openshift_username}-managed
----
+
Expected output: one ReleasePlan in your tenant namespace and one ReleasePlanAdmission in the managed namespace.

== 3. Monitor the Release Pipeline

The Release object triggers TWO pipelines that run in sequence:

1. **Tenant pipeline** (`tenant-release.yaml`) — runs in your tenant namespace
   * Purpose: User-defined validation checks
   * Allows developers to add custom validation logic before enterprise checks
   * Fails fast if basic requirements aren't met
   * Runs with tenant namespace permissions

2. **Managed pipeline** (`managed-release.yaml`) — runs in the managed namespace
   * Purpose: Enterprise compliance validation and production promotion
   * Validates against Enterprise Contract policy (security, compliance, attestation requirements)
   * Only runs if the tenant pipeline succeeds
   * Pushes the verified image to production Quay on success
   * Runs with managed namespace permissions (platform team controls)

This two-stage architecture separates developer concerns (tenant) from organizational compliance requirements (managed).
You will observe both pipeline runs from the Release detail view.

. On the Release detail page, click the *Pipeline runs* tab.
+
.Konflux Pipeline runs tab showing tenant and managed pipelines
image::module-06-pipeline-runs.png[Konflux Pipeline runs tab showing both tenant and managed pipeline runs,800]
+
You will see two pipeline runs:
+
[cols="1,1,3",options="header"]
|===
|Pipeline |Type |Purpose
|**Tenant** (e.g., `tenant-9ktp9`)
|User checks
|Custom validation logic defined by your team. In this lab it performs a simple snapshot validation. In production you might add functional tests, security scans, or deployment readiness checks.
|**Managed** (e.g., `managed-9gqjh`)
|Enterprise compliance
|Platform-enforced validation: Enterprise Contract policy evaluation, signature verification, SLSA attestation checks. Only this pipeline can push to production. Controlled by the platform team, not individual developers.
|===

. Wait for both pipelines to complete.
The tenant pipeline runs first and typically completes quickly (under 30 seconds).
The managed pipeline runs second and takes 2-3 minutes.

. Wait for the Conforma evaluation task to complete.
In the task logs, confirm the result is *Pass*.
+
If the Conforma task fails, the pipeline stops and the image is not pushed to production.
Read the failure message in the task logs — it identifies the exact policy rule that blocked the release.
+
NOTE: A Conforma failure at release time means either the policy changed between the Module 5 check and now, or the artifact was altered after the integration check passed.
That is precisely the protection this architecture provides.

. Wait for the image push task to complete.
In its logs, find the line showing the production image reference — the full Quay URL and digest of the promoted image.
Copy this reference.

. In the terminal, store the production image reference:
+
[source,text]
----
export PROD_IMAGE=<paste the full production image reference including @sha256:digest>
----

. Monitor the release pipeline until it reaches *Succeeded*.

. In the terminal, confirm the Release reached a successful state:
+
[source,bash,role="execute",subs="attributes+"]
----
oc get release -n {openshift_username}-tenant -o yaml | grep -A 15 'conditions:'
----
+
Expected output: a conditions list that includes an entry with `type: Released` and `status: "True"`.

== 4. Verify the Production Artifact and Supply Chain Integrity

The image is in production.
You now confirm three things: the digest in the production registry matches the build digest from Module 3 (no rebuild occurred), the cryptographic signature is valid on the production reference, and the SLSA provenance attestation traveled alongside the image.
Then you walk the full supply chain to confirm every link is traceable from source commit to production.

. Switch to the *Quay* tab and navigate to the `tsf` organization.
+
The production image is in the same `tsf` organization as your development images, in the same repository (`{openshift_username}-tenant/sample-component-golang-XXXXX`), but with the `production` tag instead of `on-push-<commit>`.

. Locate your component repository (`{openshift_username}-tenant/sample-component-golang-XXXXX`) and find the newly released `production` tag.
Confirm the push timestamp matches the time the release pipeline ran.

. Click the image tag and note the digest shown in Quay.
Compare it with the digest in `$PROD_IMAGE` — they must be identical.
Image promotion copies the existing artifact; it does not rebuild it.

. In the terminal, verify the cryptographic signature on the production image:
+
[source,bash,role="execute",subs="attributes+"]
----
cosign verify \
  --certificate-identity-regexp 'https://konflux.*' \
  --certificate-oidc-issuer {tas_oidc_issuer} \
  ${PROD_IMAGE}
----
+
Expected output: `Verification for <image> -- Verified OK`
+
The certificate identity regexp and OIDC issuer are the same values used in Module 4 — the image was signed by the same Konflux builder.
The same image digest is now tagged `production` instead of `on-push-<commit>` — the bytes are identical, only the tag changed.
+
NOTE: If `cosign verify` returns a certificate error, confirm that `$PROD_IMAGE` contains the full digest reference (`@sha256:...`) and that the `{tas_oidc_issuer}` value matches the OIDC issuer shown in your lab instructions.

. Confirm the SLSA provenance attestation is present on the production image reference:
+
[source,bash,role="execute"]
----
cosign download attestation ${PROD_IMAGE} | jq 'length'
----
+
Expected output: a number greater than zero, confirming that at least one attestation traveled with the image to the production registry.

. Retrieve the build metadata from the SLSA provenance attestation to verify traceability.
First, check which SLSA predicate version your cluster uses:
+
[source,bash,role="execute"]
----
cosign download attestation ${PROD_IMAGE} | jq -r '.[0].payload | @base64d | fromjson | .predicateType'
----
+
Then extract the source commit and builder using the matching path below.
+
.SLSA v1 — `https://slsa.dev/provenance/v1`
[source,bash,role="execute"]
----
cosign download attestation ${PROD_IMAGE} | \
  jq '.[0].payload | @base64d | fromjson |
    {repo: .predicate.buildDefinition.resolvedDependencies[0].uri,
     commit: .predicate.buildDefinition.resolvedDependencies[0].digest.gitCommit,
     pipeline: .predicate.runDetails.builder.id}'
----
+
.SLSA v0.2 — `https://slsa.dev/provenance/v0.2`
[source,bash,role="execute"]
----
cosign download attestation ${PROD_IMAGE} | \
  jq '.[0].payload | @base64d | fromjson |
    {repo: .predicate.materials[0].uri,
     commit: .predicate.materials[0].digest.sha1,
     pipeline: .predicate.builder.id}'
----
+
Expected output: a JSON object showing the source repository URL, the commit SHA from your Module 3 code push, and the Konflux builder identifier.
+
This confirms that starting from the production image digest alone, any authorized party can recover the source commit, the signing event in the Rekor transparency log, and the Conforma policy evaluation that approved the release.

. Review the end-to-end chain you built across this lab:

== Learning Outcomes Checkpoint

Before moving on, check that you can answer the following:

*Why does the release pipeline re-evaluate Conforma policy instead of trusting the Module 5 result?*

Policy bundles change over time.
A new vulnerability rule or compliance requirement might be published after your integration test passed.
Re-evaluating at release time ensures the artifact meets the policy that is current right now — not the policy that was current when the build ran.
If the artifact was tampered with after Module 5, the signature check embedded in Conforma also catches that.

*Why is the production image digest identical to the build digest?*

Konflux promotes the existing, signed artifact rather than rebuilding it.
Rebuilding from the same source would produce a different image — timestamps, layer ordering, and other non-deterministic factors vary between builds, and a new build would invalidate the existing signature.
Promotion copies the immutable artifact: same bytes, same digest, same signature, same provenance.

*How does the ReleasePlan / ReleasePlanAdmission model enforce separation of duties?*

Your team controls the ReleasePlan in your tenant namespace.
You choose when to request a release and for which Application.
The platform or security team controls the ReleasePlanAdmission in the managed namespace.
They define the policy bundle, the pipeline, and the list of Applications permitted to release there.
Neither side can complete a release without the other, and neither can weaken the other's controls.
An attacker who compromises your tenant namespace cannot change the release policy because that lives in a namespace they cannot write to.

*Starting from a production image digest, what supply chain evidence can you retrieve?*

Everything.
The SLSA provenance attestation links the digest to the source commit and the build PipelineRun.
The cosign signature links the digest to the signing event in the Rekor transparency log.
The Release object in your tenant namespace links the digest to the Conforma policy evaluation that approved the release.
No gap exists between the production artifact and its complete build history.

== Key Takeaways

* The ReleasePlan / ReleasePlanAdmission model separates release requests (application team, tenant namespace) from release governance (platform team, managed namespace). No single team controls both sides of the gate.
* The release pipeline re-evaluates Conforma policy at release time. Policy changes between build and release are caught, not bypassed.
* Image promotion copies the immutable digest built and signed in Module 3. No rebuild occurs and no new artifact is introduced.
* Attestations — SBOM and SLSA provenance — travel with the image because Quay stores them in the same repository keyed to the same digest.
* End-to-end traceability is the core value: starting from a production image digest, any authorized party can reconstruct the full supply chain history — source commit, build, signing event, policy evaluation, and release approval.
* This pipeline aligns with SLSA Level 3 requirements: isolated build environment, signed provenance, policy-gated promotion, and a tamper-evident transparency log.
